# 8-Puzzle Search Algorithms Visualizer

An interactive web app that solves the **8-puzzle** with three uninformed search algorithms, **BFS**, **DFS** and **IDS**, and draws the *actual* search tree each one builds, step by step.

## Features

- **Random solvable puzzles** with four difficulty levels (Easy, Medium, Hard, Fully random).
- **Real search tree**: every node on screen was generated by the algorithm. Nothing is precomputed or faked.
- **Full playback controls**: Run, Pause, Resume, Step, Skip to end, Reset and five speed levels.
- **Live statistics**: generated nodes, expanded nodes, max frontier size, max depth, solution length (plus the depth limit and iteration number for IDS).
- **Solution path view**: the sequence of boards from the initial state to the goal.
- **Algorithm comparison**: runs all three algorithms on the same puzzle without animation and compares results and real execution time.

## How to use

1. Pick a **difficulty**. Changing it creates a new puzzle. The initial and goal boards are shown at the top left.
2. Choose an algorithm: **BFS**, **DFS** or **IDS**. For DFS you can also change the depth limit.
3. Press **Run** to animate the search, or **Step** to advance one event at a time. Use **Pause / Resume** at any moment and the **Speed** slider to change the pace.
4. Watch the tree grow, read the **Statistics** panel, and see the **Solution path** when the goal is reached.
5. Press **Compare all algorithms** to run BFS, DFS and IDS on the current puzzle and compare them side by side.

### Reading the search tree

Each tree node is a small board. The header shows the direction the **empty cell** moved to create it (`↑ ↓ ← →`) and the node's depth (`d3`).

| Color | Meaning |
|---|---|
| Amber | **Frontier**: generated but not expanded yet |
| Blue | **Expanded**: its children have been generated |
| Green | Part of the **solution path** |
| Red, dashed | **Pruned**: reached the depth limit, so it is not expanded |
| Purple ring | The node touched by the most recent event |

Large trees are expensive to draw, so the **Render up to** selector limits how many nodes are drawn. The solution path is always drawn, and the statistics always count every node.

## Algorithms at a glance

Each algorithm has its own documentation with logic, pseudocode, implementation notes and complexity:

- [Breadth-First Search (BFS)](docs/BFS.md)
- [Depth-First Search (DFS)](docs/DFS.md)
- [Iterative Deepening Search (IDS)](docs/IDS.md)

| | BFS | DFS (depth-limited) | IDS |
|---|---|---|---|
| Frontier | FIFO queue | LIFO stack | LIFO stack, one pass per depth limit |
| Complete | Yes | Only if the limit is at least the solution depth | Yes |
| Optimal (fewest moves) | Yes | No | Yes |
| Time | O(b^d) | O(b^m) | O(b^d) |
| Memory | O(b^d) | O(b·m) | O(b·d) |

`b` is the branching factor, `d` the depth of the shallowest solution and `m` the depth limit. For the 8-puzzle `b` is about 2.67 on average (about 1.67 after excluding the move that undoes the previous one), and the optimal solution depth is at most 31.

Example run on the same puzzle (initial state `0 5 2 1 8 3 4 7 6`, solution depth 8):

| | Path length | Generated | Expanded | Max frontier |
|---|---|---|---|---|
| BFS | 8 | 155 | 92 | 63 |
| DFS (limit 12) | 8 | 60 | 34 | 12 |
| IDS | 8 | 376 | 209 | 8 |

IDS generates more nodes than BFS because it rebuilds the upper levels in every iteration, but it needs far less memory. DFS happened to be lucky here. It does not guarantee a shortest path.

## How it works

### Puzzle model

A state is an array of 9 numbers in row-major order, where `0` is the empty cell. The goal is `[1, 2, 3, 4, 5, 6, 7, 8, 0]`. Moves slide the empty cell in a fixed order (Up, Down, Left, Right), so every run is deterministic.

### Solvable puzzles

Only half of all permutations can reach the goal. On a 3×3 board a state is solvable if and only if its **inversion count** (ignoring the empty cell) is even.

- *Fully random* shuffles the tiles until the state is solvable.
- *Easy / Medium / Hard* start at the goal and make random moves, so the puzzle is solvable by construction and its optimal solution depth is at most the number of moves.


### Safety limits

- DFS has a configurable depth limit (default 20) because the state graph has cycles and unlimited DFS can wander extremely deep.
- Every algorithm stops with a `node-limit` failure after 200,000 generated nodes (`MAX_GENERATED` in `src/App.jsx`). This is mostly relevant for DFS and IDS on *Fully random* puzzles.

## Configuration

| Setting | Where | Default |
|---|---|---|
| Node limit | `MAX_GENERATED` in `src/App.jsx` | 200,000 |
| DFS depth limit | Controls panel | 20 |
| IDS maximum depth | `maxDepth` option in `src/algorithms/ids.js` | 31 |
| Animation speeds | `SPEEDS` in `src/hooks/useSearchRunner.js` | 5 levels |
| Difficulty levels | `DIFFICULTIES` in `src/utils/difficulty.js` | 6 / 10 / 14 moves / random |

## Known limitations

- Statistics show node counts only. Execution time is measured in the comparison table, because animation delays would make a per-run timer meaningless.
- On *Fully random* puzzles, DFS and IDS may stop at the node limit before finding a solution.
- Drawing thousands of nodes is slow in any browser, so large trees are truncated for display only (see **Render up to**).
